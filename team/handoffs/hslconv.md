## What I did

- Created `hslconv.py`:
  - `rgb_to_hsl(r, g, b) -> tuple[float, float, float]` returning **(h, s, l)** order
    (deliberately not colorsys's (h, l, s)). h ∈ [0, 360), s, l ∈ [0, 1]. Achromatic
    (r == g == b) returns h = 0.0, s = 0.0 by convention. Type check rejects non-int including
    `bool` with TypeError; out-of-range ints raise ValueError.
  - `hsl_to_rgb(h, s, l) -> tuple[int, int, int]`: h ∈ [0, 360) (360 excluded), s, l ∈ [0, 1];
    channels quantized **half-up** via `int(floor(x·255 + 0.5))` (never banker's `round`).
    Non-numeric types (including `bool`, strings) raise TypeError; out-of-range/NaN raise
    ValueError.
- Created `tests/test_hslconv.py` (28 tests) covering every acceptance bullet verbatim:
  fixed points for red/green/blue/yellow/black/white/gray, the five `hsl_to_rgb` fixed points,
  tuple-order guard test, ValueError cases (256, -1, h=360, h=-1, s=1.5, l=-0.1), TypeError
  cases (1.5, True, "0"), plus properties: random RGB vs `colorsys.rgb_to_hls` (hue compared by
  circular distance, hue converted from turns to degrees; achromatic handled per our
  convention), random HSL vs `colorsys.hls_to_rgb` with half-up quantization, and round-trip
  `hsl_to_rgb(*rgb_to_hsl(r, g, b))` within 1 per channel.

Key subtlety found while validating: stdlib `colorsys` takes hue in **turns [0, 1]**, not degrees,
and orders the triple **HLS**. Both test properties account for that (`h / 360.0` and
`h *= 360.0` respectively).

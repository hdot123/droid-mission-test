# 板面关单翻板 · 调查结论与最小操作指引

**状态**：repo 侧不可修（证据链见下），需大哥在 Projects #33 侧改一条内建自动化规则。
**现象来源**：第 52 轮活验核验报告 Steelman 第 1 条（`adversarial/round52-verify/verify-live.md`，只读底稿）；对应验证断言 VAL-M3-005。

## 现象

A/C/D 三单在 assemble 窗内由 PAT 写板为「已验收」（`closeout.project_state_written=true`），但人工关单后 1–2 秒，板面 Status 被翻回「施工中」：

| 工单 | 写板「已验收」 | 关单（ClosedEvent） | 翻板「施工中」 | 翻板演员 |
|---|---|---|---|---|
| #761 | 22:53:50Z | 23:59:40Z | 23:59:41Z | `github-project-automation` |
| #763 | 23:03:57Z | 00:01:05Z | 00:01:06Z | `github-project-automation` |
| #764 | 22:47:13Z | 00:00:18Z | 00:00:20Z | `github-project-automation` |

证据：`timelines.json`（三单 timeline 逐事件）、`projects33.json`（板面当前值）。三单时序同构：翻板紧跟关单、演员一致。

## repo 侧排查（为什么不可修）

1. **仓内没有任何产生该演员的写入点**：全仓 grep `github-project-automation` 零命中；Actions 侧唯一的板面写点是 `scripts/team/project_state_write.py`（assemble 的 `Write Projects board via PAT` 步），演员为 PAT 持有人（hdot123），与翻板演员不同。
2. **翻板发生在 workflow 结束之后**：写板步在 assemble 窗内（22:47–23:04），关单在 30–60 分钟后由人工完成，此时 workflow 早已结束，repo 侧没有任何在「工单被关闭」事件上触发的自动化（`team.yml` 只触发于 issue 评论/开启）。
3. **`github-project-automation` 是 GitHub Projects 内建自动化的系统演员**：Projects 设置里配置的内建工作流（如「Item closed → Set Status」）在时间线上就以该身份记账。翻板与关单秒级同构，正是「项目内建工作流：当 item 关闭时把 Status 设为施工中」的行为。

结论：翻板不是流水线代码造成的，repo 内无可拦截、可修正的写入点；修改仓库代码（例如收口后重写板面）无法覆盖「workflow 结束后人工关单」这个时刻。

## 需大哥侧动作（最小操作，一条规则）

1. 打开 Projects #33 → 右上 `⋯` → **Workflows**（工作流）。
2. 在 **Built-in（内建）** 分组找到 **「Item closed」** 工作流（中文界面显示为「当项目中的项被关闭时…」）。
3. 该规则当前把 Status 设为 **施工中**。二选一：
   - 若不再需要：把该工作流的 **Set Status** 步骤删除，或直接用开关 **Disable** 整条规则；
   - 若希望「关单即终态」：把 Set Status 的目标选项从 **施工中** 改为 **已验收**（或你认定的关单终态选项）。
4. 保存。其余内建规则（Auto-assign、Item reopened 等）不在本次现象链上，可不动。

## 3. 打回理由：cancelled / 图级 skip 漏收

审查标准明确要求：**失败和 timeout/cancelled 能跑写账**。下列路径 **已用代码查实**，且 **死亡矩阵 / lint 未覆盖**。

### 3.1 lead `cancelled` 时 chain.worker 不落账（漏收）

**代码路径：**

```yaml
# workers-wall-merge job if（PR 688）
always() && !cancelled() && ... &&
(needs.lead.result == 'success' || needs.lead.result == 'failure')
```

- 当 `needs.lead.result == 'cancelled'`：**整个 workers-wall-merge job 被 skip**。
- `worker` matrix 因 `needs.lead.result == 'success'` 本也不会跑 → `chain.worker` 保持 **init 快照 `unknown`**，不会像 lead-failure 那样用 `needs.worker.result == 'skipped'` 入账。

**对比已修路径：** lead **failure** 时 merge 会跑并写 `skipped`（`normalize_chain_job_result` 支持 `skipped` → `summary_code=not_started`）。

**复现方式（图级，尚未在本席跑 live workflow）：** 对进行中 run 取消 lead job，或令 lead 结论为 `cancelled`；下载 `foreman-run-${{ run_id }}`，断言 `chain.lead` 可为 `cancelled`（lead 步无 `!cancelled()`），但 `chain.worker.result` 仍为 `unknown`。

### 3.2 工作流 `cancelled()` 时多席「Record exit」步被 `!cancelled()` 挡住

下列写账/上传步带 **`always() && !cancelled()`**（步级或 job 级），当 **workflow 被 cancel** 时 GitHub 将 `cancelled()` 置真，步 **不执行**，即使 job 已部分执行：

| 位置 | 步/ job |
|------|---------|
| workers-wall-merge | job `if` 含 `!cancelled()`；`Record worker job exit` L795 |
| replan | `Record replan exit` L1947；upload L1968 |
| workers2-wall-merge | job `if` L2287；`Record worker2 job exit` L2315 |

**对比：** lead `Record lead exit` **无** `!cancelled()`（L413），故 lead cancelled 仍可能落账；replan/worker 合并链在 **workflow cancel** 下仍可能漏写。

**尚未查实：** 本席未点火 live run 下载 artifact 断言；缺 **Actions run id + artifact 快照** 作为运行时证据。代码路径证据充分，结论成立。

### 3.3 replan `cancelled` 时 workers2 合并链不跑

`workers2-wall-merge` 仅 `replan.result ∈ {success, failure}`（L2286–2288）。replan **cancelled** 时与 §3.1 同类漏收（`chain.worker2` 可能停留 `unknown`）。

### 3.4 死亡矩阵未钉死图级 cancelled / validate2

**已复现（本地 pytest）：**

```bash
pip install -r requirements-dev.txt
python3 -m pytest tests/test_foreman_wall_contract.py \
  tests/test_foreman_wall_failure_paths.py \
  tests/test_foreman_wall_death_matrix.py \
  tests/test_gh_project_parse_contract.py -q
# → 55 passed（PR 头 checkout）
```

`test_foreman_wall_death_matrix.py` 的 `DEATH_MATRIX` **不含** `validate2`、`worker`+`cancelled`、图级 `lead cancelled → worker`；均为 **脚本级** `wall_sync_job` / `sync_assemble_exit` 单测，**不能** 替代 workflow `if` 图灵验收。

`lint_workflow_wall_exits.py` 仅断言步文本含 `always()`，**不** 解析 job 级 `needs.*.result` 集合是否包含 `cancelled`。

## 7. 结论与退回条件

### 总结

**打回。**

### 已查实

1. main 上 lead 写账步无 `always()` 且 `--result success` 写死（W-9 病根）。
2. PR 对 lead failure/timeout 及全席 `always()` 写账 + merge 在 lead/replan **failure** 下续跑，prep2/assemble-exit 符合批二描述。
3. 本地 pytest 55 绿；lint 双绿；PR 头 CI contract 绿。
4. lead **cancelled** 时 workers-wall-merge 不跑 → `chain.worker` 可能仍为 `unknown`。
5. workflow **cancelled()** 时多处 `!cancelled()` 阻止 Record exit。
6. replan **cancelled** 时 workers2-wall-merge 不跑。
7. 死亡矩阵未覆盖上述图级路径。

### 尚未查实（缺证据）

1. live Actions 上 cancel lead / cancel workflow 后的 `foreman-run` artifact 字节级快照（需一次可控点火 run，本席未执行）。
2. validate2 job 结论 `cancelled` 时派生写账是否与 `job.status` 一致（仅静态步存在，无矩阵用例）。

### 建议退回后最小闭合（供开发席，非本席实施）

1. `workers-wall-merge` / `workers2-wall-merge` 的 job `if` 在 fail-closed 前提下纳入上游 `cancelled`，并在上游 cancelled 时仍将 worker 记为 `skipped`（与 lead-failure 对称）。
2. 评估 Record exit 步上 `!cancelled()`：在 workflow cancel 场景仍保留 **已启动 job** 的落账（与 lead 步对齐）。
3. 死亡矩阵或 workflow 结构测试增加：`lead|replan cancelled` → merge 行为 + `chain.worker|worker2` 非 `unknown`。

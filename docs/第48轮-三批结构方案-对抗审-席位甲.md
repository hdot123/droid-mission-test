## 2. 三批方案分项审评

### 批一：写板类 —「唯一拆包口」+ 契约测试 + 分页

**席位甲立场：原则认可，范围与信封模型必须收窄后施工。**

#### 2.1.1 现码核对

- W-1 已在 main 闭合：`parse_project_item_list` 处理 list / `{"items":[...]}` 两种形（见 `foreman_run_lib.py` L168–175；`project_state_write.py` L41–41）。
- W-8（方案与 #680 补丁语境中的 `field-list` 信封）在 main **未闭合**：同一文件 L87–91 仍 `json.loads(fr.stdout or "[]")` 并假定顶层为 **array**；若 CLI 返回 `{"fields":[...]}`（与 item-list 同族），`pick_status_option` 会在静默错误或异常中暴露，且**不共享** `parse_project_item_list`。
- `--limit 200` 仍硬编码于 item-list（L33–34），无 cursor/分页；工单量或板面 item 数超限时，「找不到 item」可与 W-1 **症状相同、根因不同**。
- workflow 内仍有大量内联 `json.loads(gh ...)`（如 lead 计划步 `issue list` L290–292、`team.yml` 评论分页 L92–93），**不经过**任何 Python 拆包口；批一若只改 `project_state_write.py`，不能兑现「想漏都没地方漏」。

#### 2.1.2 认可部分

- 「同族手写拆包」作为 47/48 轮写板失败的模式判断**正确**。
- 抽出共用解析 + 契约测试，与 `foreman-run.v1` 硬化路线一致。

#### 2.1.3 反对 / 须收窄部分

- 把 W-1 与 W-8 说成「同一个病」：**过度合并**。更准确表述为 **同一病族（GitHub Projects CLI JSON 信封不统一）下的两个实例**；拆包函数须按 **命令/资源** 分型（`item-list` / `field-list` / `project view`），不能用一个 `parse_project_item_list` 包打天下。
- 「唯一拆包口」在**多种信封 + workflow 内联 gh** 并存时**不可达**，除非批一明文包含：（甲）`scripts/team/gh_projects.py`（或同等模块）为 **唯一** `subprocess gh project` 调用层；（乙）`team.yml` 内联 gh JSON 解析迁出或 lint 禁止；（丙）分页策略写进同一模块并带集成测试。
- 契约测试「真实返回形状」：**禁止**手搓 fixture 冒充生产信封为唯一依据；应规定 **录制-回放**（CI 用脱敏 snapshot）+ **最小合成 fixture** 双轨，且合成 fixture 必须来自录制样本的子集，防止「测过的假形状」。

### 批二：失败留痕 —「每步自记账，汇总只拼装」

**席位甲立场：方向认可；与统一墙的冲突点必须用 schema 写死，否则反对按现表述施工。**

#### 2.2.1 现码核对：W-2 与 W-9 是否同病

| 代号 | 现象（任务描述 + 47 轮文档） | main 机制 |
|---|---|---|
| **W-2** | 写板失败写 `project_state_enum=null` 撕 schema | **已修**：失败只写 `run_must_fail` + `project_state_error`，成功才写 enum（`project_state_write.py` L116–127；`test_w2_board_write_fail_omits_null_enum`） |
| **W-9** | 领班早死、墙账少更新、根因存疑 | **部分成立**：lead job 仅在成功路径调用 `wall_sync_job --job lead --result success`（`team.yml` L412–430）；**无** `if: always()` 的 lead 失败/超时补账。lead droid `timeout 600s`（L198）后，若未进入 plan 步，chain.lead 仍为 env-check 初始 `unknown`，**budgets.session_outcome 亦无 lead 记录** |

**结论：W-2 与 W-9 不是同一病。**

- W-2：**单步写墙内容违反 schema**（closeout 字段类型），属于「记账内容错了」。
- W-9：**链路过早中断导致记账步未执行**（lead 缺兜底 sync），属于「记账时机错了」。

方案把它们并为批二，在**诊断层误归**；在施工层仍可同批处理，但文档必须改写，否则归因和验收都会漂。

#### 2.2.2 validate 路径对照（说明批二并非从零开始）

validate 路径已基本符合「死了也记」：`adopt_verdict.py` 在 `always()` 下合并 `validation` + `human_stop` + `closeout.run_must_fail`（L255–280）；这与方案描述一致。批二**真正缺口**在 **lead、replan 会话步**（及可能的 worker droid 步与 delta 上传之间的缝隙），而不是 validate。

#### 2.2.3 与唯一 ForemanRun 墙是否冲突

现设计已是 **多 job patch-merge 同一 `foreman-run.json` artifact**，非多文件分墙。方案「每岗位自写账」若理解为：

- **可接受**：各 job 尾步 `load_wall → deep_merge(patch) → save_wall(validate_schema)`，汇总步 `assemble` 只读墙 + 投影 artifact。
- **不可接受**：各 job 写独立账本再异步拼墙；或允许无 schema 校验的中间 JSON。

**竞态**：GitHub Actions artifact 为 **last-upload-wins**；并行 worker 通过 `merge_worker_deltas.py` 合并后再 `wall_sync_job`（`team.yml` L776–785），这是已选的串行化点。批二加 lead `always()` sync 时，必须保持 **单写者顺序**（先 patch chain/budgets，再 upload），避免与 worker-wall-merge 交叉覆盖。

#### 2.2.4 `assemble_chain_facts.py` 缺口

脚本已实现从 `needs.*_RESULT` 补 chain_facts（`assemble_chain_facts.py`），但 **assemble job 未调用**。48 轮「汇总只拼装」在现码下**不成立**：无 verdict 时 assemble 仍靠内联 Python + `pick_verdict_from_wall.py`，链事实可能长期停留在上游 job 未 sync 的默认值。批二施工必须把该脚本 **接入 assemble** 或等价逻辑，并 lint 禁止与墙 `chain` 矛盾的静态文案。

#### 2.2.5 批二认可的验收提议（改写后）

方案要求「每阶段模拟死一次、账本必有记录」：**认可**，但须按 job 列矩阵，且 **lead failure** 与 **board write failure** 分列（后者已测，前者未测）。

### 批三：会话超时 — 采认外移、分步落盘、心跳

**席位甲立场：核心结构点（采认与 droid 会话解耦）认可；「不再进死亡账」提法危险，须删改。**

#### 2.3.1 现码：验收员超时与 fail-closed

- 预算：`budgets.roles.validator.droid_wall_sec=480` + GNU `timeout 600s`（`foreman_run_lib.py` L42–46；`team.yml` L1343–1348）。
- 超时：`droid_exit==124` → `adoption_status=failed` / `draft_timeout` / `human_stop=True` / `run_must_fail`（`adopt_verdict.py` L105–107、L255–260）。**这是正确的 fail-closed**，不是 bug。
- 48 轮 A：**合法长回复吃光预算**导致采认失败，墙上有记录（`i8_summarize_run.py` 对 scene A 的 PASS 条件即检查 `adoption_status=failed` + `human_stop`）。

方案 ①「签字搬出会话」：**与现架构缺口对齐** — 当前 validate job 内仍有「droid 合并 verdict」与「adopt 落墙」串联；采认外移可避免 **会话死掉导致 verdict.json 物理缺失**，但不能把 `human_stop` 摘掉。

方案 ②领班分步落盘：**对齐 W-9**。lead 现一整段 droid 写 `team-plan.json` 再才落计划 issue（L151–430），中途死则 plan artifact 与墙皆空。分步落盘是结构改法，不是 10→15 分钟能替代的。

方案 ③心跳：**现无实现**。`stream-json` tee 到 `lead-stream.jsonl` / `validator-stream.jsonl` 已存在，但无「stall detector」步。

#### 2.3.2 预期效果措辞风险

「超时从整单死亡降级为这一步重跑，**不再进死亡账**」——**反对按字面施工**。

- 凡采认失败、板面写失败、pytest 闸失败，墙上仍必须有 `human_stop` / `run_must_fail` / job 红；这是产品 fail-closed 要求。
- 可承诺的仅是：**下游不必因上游会话超时而丢失 chain_facts / adoption_error**（信息不再「白死」），且 **编排上允许人/脚本在合规门内重跑该 job**，不是把失败从账上抹掉。

#### 2.3.3 采认外移 — 草稿不完整时脚本签字

**反对**任何「无草稿仍 overall=pass」的脚本捷径。外移采认步必须复用现 `adopt_verdict.py` 门：

- `judgeable` 非空且无 `verdict-droid.json` → `missing_draft`；
- 覆盖不匹配 → `coverage_mismatch`；
- 仅当 draft 完整且 manifest 未篡改时才 `adoption_status=ok`。

外移后若用 shell 拼接 verdict，**必须**走同一 Python 模块，禁止第二套宽松逻辑。

#### 2.3.4 10→15 分钟

`foreman_run_lib.default_budgets()` 中 lead/replan `job_wall_min=15` 已与 job `timeout-minutes: 15` 对齐；validator **仍是 12 min job / 600s droid**。把 10→15 当主药：**反对**。在 48 轮 A 场景下，加长只延后 `draft_timeout`，不解决「签字与会话同槽」；与方案自述矛盾。

#### 2.3.5 心跳：长回复 vs 卡死

无现成区分器。对抗要求：

- **不得**仅用「N 秒无 stdout」杀会话 — 会误杀合法长回复（48 轮 A 二次长回复即反例）。
- 可行方向：解析 `stream-json` **事件时间戳** +「末条消息类型」；区分 `stall`（无事件 > T_stall）与 `budget`（总时长 > T_budget）；`T_stall` 应显著小于 `T_budget` 且仅用于 **提前 fail + 落墙 `droid_failed`**，不是 silent cancel。
- 误拐风险无法降到零时，验收须保留 **I8-A 活题** 回归（合法长回复不得被判 stall）。

## 3. 八大质疑正面回应

### 质疑 1：W-1 与 W-8 是否同病？唯一拆包口可否覆盖第三种信封？

- **同病族、不同实例**（见 §2.1）。
- 第三种信封 **一定会再出现**（`project view` 已是裸 dict；`field-list` 疑似第二种）。「唯一拆包口」应定义为 **按命令分派的解析表 + 共用分页/错误归一**，而非一个 list 解析函数。
- 契约测试：必须 **录制样本驱动** + CI 禁止未登记信封（见 §2.1.3）。

### 质疑 2：W-2 与 W-9 是否同病？

- **否**（见 §2.2.1）。方案应改写病因表；W-2 在 main 已闭合，批二应聚焦 **未兜底 job**（lead 为首）。

### 质疑 3：每岗位自记账 vs 唯一 ForemanRun？

- **不冲突**，前提是：单 artifact、每次 `save_wall` 过 schema、无第二权威文件（见 §2.2.3）。
- **风险点**：并行 upload 竞态 — 须维持 worker merge 串行点；新增 lead `always()` sync 不得破坏 upload 顺序。

### 质疑 4：批三是否削弱 fail-closed / 假绿 / 误采认？

- 按现表述 **会削弱**（「不再进死亡账」）。
- 收窄后：**不削弱** — 外移采认须硬编码 fail 门（§2.3.3）；「重跑」限于 **人工或显式新 run**，禁止自动重跑把失败洗绿。

### 质疑 5：心跳 vs 合法长回复？

- 现码 **无** 区分；单纯心跳 **高危误拐**（§2.3.5）。
- 批三若上心跳，必须 **双阈值 + stream 语义**，并绑 I8-A 回归。

### 质疑 6：10→15 是否仍用时长掩盖？

- **是（若作为主药）**。仅可作为批三「顺带旋钮」，且须同步改 `budgets` schema 字段与活验题面声明，不能单独 merge。

### 质疑 7：三批全合再同题复验？

- **反对**作为唯一验收策略。批间无法归因，前批回归会被后批掩盖。
- **必改**：每批合并前 **最小隔离活验**（至少：写板路径、lead 早死、validate 超时采认各 1 题）；三批全合后再跑 47/48 **同题全集** 作终验。

### 质疑 8：根治还是改口叫结构？

- **兼有真结构与补丁换名风险**。
- 真结构：gh 解析层、lead 分步、采认外移、assemble chain_facts 接线。
- 换名风险：若批一不动 workflow 内联 gh、批二不接 assemble_chain_facts、批三只加分钟 —— 本质仍是补丁清单，不配「根治」。

## 1. 总判

| 维度 | 结论 |
|---|---|
| **三批结构方案作为战役第 49 轮前的施工蓝图** | **有条件通过** |
| **指挥先前对该方案的口头「根治」批准** | **应收窄** — 方向里「结构分包」与「一面 ForemanRun 墙」不矛盾的部分可保留；**不得**按字面理解为「已根治」或「三批一次合入即可同题复验绿灯」 |

**一句话**：方案把第 48 轮已暴露的三类病灶（写板拆信封族、失败不上墙、会话预算连坐）归并成三批，**大方向与仓内事实相容**；但批内多处仍是 **workflow 补 `always()` + 抽 parse 函数** 的「补丁打包」，不是已全部设计闭合的架构换代。施工前必须拆开误归并（W-2≠W-9）、补齐单拆包口边界、**强制每批隔离活验**，否则同题复验无法归因，也难证明「根治」。

## 3. 八项强制质疑 — 正面回应

### 3.1 W-1 与 W-8 是否同病？「唯一拆包口」能否覆盖？契约测试会否造假？

**同病（族）成立，同补丁不成立。**

| 项 | 仓内事实 |
|---|---|
| W-1 | `parse_project_item_list()` 已存在，仅用于 `item-list` 的 `items` 键（`foreman_run_lib.py` L168–175；`project_state_write.py` L40–41） |
| W-8 | **未修**：`field-list` 仍 `fields = json.loads(fr.stdout or "[]")` 直接进 `pick_status_option`（`project_state_write.py` L87–91），dict 信封会炸 |
| 第三种形状 | `project view` 用 `json.loads(pr.stdout).get("id")`（L50–53）——已是 object 根，不是 list；`i8_wait_for_job.py` 对 `gh run view --json jobs` 用 `.get("jobs")`（L30）——**第三条拆包范式** |
| 散布点 | `team.yml` 内联 `gh`：`issue` 评论分页（L85–96）、`issue list`（L290–292）各自手写；**不是**只有 `project_state_write.py` 两处 |

**对「唯一拆包口」的对抗结论**：

- **可做**「`gh project * --format json` 专用层」：`parse_item_list` / `parse_field_list` / 分页迭代**共模块**，禁止业务侧 `json.loads` 后当 list 用 —— 这是真结构收口。
- **不能**用**一个**函数假装覆盖 GitHub Projects API 全部信封；必须按 **命令契约** 分形（items / fields / project id / GraphQL 若未来引入）。
- `--limit 200` 无翻页仍潜伏（`project_state_write.py` L33–34）；批一若只做 W-8 不修分页，**不算根治写板族**。

**契约测试「真实形状」**：

- 可行来源：`tests/test_foreman_wall_failure_paths.py` 已用 mock `_gh` stdout（W-1/W-2 范式）；升级方向是 **录制固定 fixture**（redacted PAT 环境跑一次 `gh project item-list/field-list` 写入 `tests/fixtures/gh-project/`），CI 只读文件，**禁止**手搓与 CLI 版本漂移无关的 dict。
- 造假风险：若契约仅复制作者脑海中的 `{"fields":[...]}` 而未绑定 `gh` 版本，**能通过单测仍活验炸** —— 方案须写明 fixture 更新流程与 CLI pin。

### 3.2 W-2 与 W-9 是否同病？误归并则须明说

**不是同病；批二表述若合并二者，属误归。**

| 编号 | 机制 | 现码 |
|---|---|---|
| **W-2** | 写板失败时 `closeout.project_state_enum=null` → `save_wall` schema 拒收，**连失败痕迹都写不进墙** | 已修：`project_state_enum` 仅成功写入（`project_state_write.py` L116–127；单测 `test_w2_board_write_fail_omits_null_enum`） |
| **W-9** | 领班 **早死/超时** 时 **`chain.lead` 从未 sync**，工件停留在 env-check 初始墙；非 schema 吞账 | `Patch and upload ForemanRun wall (lead)` **无 `always()`**，且 `--result success` 写死（`team.yml` L412–430）；droid 步无 `droid-exit`+墙同步兜底 |

**对比 validate（反证批二思路已在半条链落地）**：`adopt` / `wall_sync` / upload 多处 `if: always()`（L1477–1545）；工人 `Record worker delta` `always() && !cancelled()`（L726–737）。

**批二若写「W-2、W-9 同一个病」**：对抗席 **反对** — 应改为 **「汇总步不是唯一记账人」** 的共性叙事，下分：

- W-2：**记账内容非法**（schema fail-closed 正确，曾经 Implementation bug）
- W-9：**记账步未执行**（workflow 缺口）

归并为同批施工可以（都改「何时写墙」），**不得**归并为同一根因，否则验收用例会漏测 schema 路径。

### 3.3「每岗位自写账、汇总只拼装」vs 一面墙 / 唯一 ForemanRun

**不必然分墙，但有竞态与权威语义风险。**

- 现行模型已是：**唯一 artifact** `foreman-run-${{ github.run_id }}`，各 job download → `deep_merge` → upload（W1 注释链）。
- 「每步自记」= 各 job 末 `wall_sync_job` / `foreman_run_patch` / 专用 slice writer —— **与 v2.7 设计一致**，不是第二权威。
- **风险点**（方案未写清则必翻车）：
  1. 同 job 内多步写同一文件无锁 —— 须串行步序保证，禁止并行 step 各写各的 `foreman-run.json` 再乱 upload。
  2. `post_comment_hard.patch_wall_comment` 在评论失败时 `save_wall` 可能因墙不合法 **warning 跳过**（L16–17）—— 评论与墙 slice 短暂不一致。
  3. assemble **仍写** `closeout` / 触发 `project_state_write` —— 汇总步不是「只读拼装」，方案不宜暗示 assemble 降权为纯 aggregator。

**必改（设计）**：规定 **slice 所有权**（谁可以写 `chain.*` vs `closeout.*` vs `validation.*`），禁止 worker job 直接改 `closeout`；汇总步只允许 **merge artifact + 写 closeout 终态**，不得覆盖 `validation.adoption_error` 等已终局字段。

### 3.4 批三「超时降级为这一步重跑、不进死亡账」— fail-closed？假绿？误采？

**对抗席：反对把「不进死亡账」作为默认预期效果表述。**

| 主张 | 审查 |
|---|---|
| 采认搬出会话 | **部分已实现**：GNU timeout 后 merge `always()` + `adopt_verdict`；批三①若指「merge/adopt 与 droid 同 shell」再拆步 —— 有增量，非全新 |
| 草稿不完整仍脚本签字 | `adopt_verdict` 对无 `verdict-droid.json` / coverage 不齐 → `missing_draft` / `coverage_mismatch`，`human_stop` + `run_must_fail`（L255–260）—— **已有 fail-closed**；拆步后须 **禁止**「仅有 stream.jsonl 即采认」 |
| 超时变「重跑这一步」 | 若墙不记 `chain.*.result=failure` / `session_outcome`，而 run 靠重试变绿 → **假绿** |
| 削弱 fail-closed | 「整单死亡降级」不能等于「validate job 可绿」；须保持 `compute_validate_conclusion`：adoption failed **或** artifact incomplete → job 红（L31–32、L69–70） |

**收窄批三预期**：允许 **工单/run 级** 可续跑（新工单或同 run 内领班分段落盘），但 **每一次预算耗尽必须在 `foreman-run.json` 留死亡指纹**（`chain_facts.summary_code` / `budgets.session_outcome`），assemble 仍可读墙判死。

### 3.5 心跳区分「长回复」与「卡死」— 48 轮 A 的误掐风险

- 48 轮叙事（#680 文档侧写，本席仅作机制参照）：**两次合法长回复**吃光供应商会话预算，Δ≈−2.1s，**非** GNU hang。
- 仓内 **无** 心跳实现；仅有 stream-jsonl `tee`。
- 若用心跳 =「N 秒无 stdout 字符」：长回复生成期 **零字节**，必误掐。
- 若用 stream-jsonl 事件时间戳 / tool-call 间隔：需解析器 + **保守阈值** + 「首字节后宽限期」—— 方案未给出算法与假阳性预算。

**结论**：心跳可作为 **P1 辅助**，**不能**作批三主药；主药仍是 **预算记账 + 输出契约门 + adopt 时间预留**（与批三其他条一致）。误掐未闭合前，**不得**承诺「卡死早掐不误杀」。

### 3.6 10→15 分钟是否仍掩盖问题？

- 现 `main`：lead job **已是** `timeout-minutes: 15`（L56），droid **600s**（L198）；validator job 需对照 —— validate `timeout-minutes: 15`（L1185 段），shell 600s。
- 方案写「10→15 顺带」：**与 lead job 外壳不完全对齐**（可能指供应商会话 10min 或历史叙述）；若施工仅拧 job 分钟数而不改 **墙上声明 vs shell vs adopt 预留** → **仍是加时长掩盖**。
- **对抗要求**：任何加时必须同步：`default_budgets()`、shell timeout、`compute_validate_conclusion` 的 `session_outcome` 三角一致；否则 **驳回该旋钮单独合入**。

### 3.7 三批全合才同题复验 — 归因与隔离活验

**反对「仅终局同题」作为唯一闸门。**

| 问题 | 说明 |
|---|---|
| 无法归因 | W-8 修了但 W-9 未修时，同题可能仍 0/4，指挥无法判批二价值 |
| 与方案自述矛盾 | 方案写「Cursor 改、两席验真才许合入」—— 若三批叠在一个 merge，**验真发生在一次 diff**，对抗席失效 |

**必改（流程）**：

1. 批一合入前：活验新工单 **仅测写板/parse**（C/D 类路径）。
2. 批二合入前：构造 **lead 故意超时** / worker 早死，断言 `chain.lead|worker` 非 `not_started`。
3. 批三合入前：慢验收 / 会话预算耗尽，断言 `adoption_error` 与 artifact 门。
4. 三批齐后 **再** 跑 47/48 同题池（新工单，禁止点 #661–665）。

### 3.8 真根治还是「补丁改口叫结构」？

| 批次 | 结构含量 | 对抗评语 |
|---|---|---|
| **批一** | 中 | 共用 parse + 分页是真结构；但若只有 2 个调用点 + 单测，**命名「根治」过大** |
| **批二** | 中低 | 本质是 **推广 validate/worker 已有的 `always()` wall sync 模板到 lead/replan** —— 必要，但是 **模式复制** |
| **批三** | 混合 | adopt 外置已半完成；分段落盘、心跳为新；**10→15** 若单列则是补丁 |

**总评**：方案是 **「分包补丁 + 少量新抽象」**，比散弹 PATCH 好，**不足以**在无语境下称为「48 轮三种死法从结构上灭绝」；需用 **隔离活验 + fixture 契约** 证明后方可升级措辞。

## 5. 必改项（施工前）

1. **拆开 W-2 / W-9 叙事**，批二验收用例分列。
2. **批一** 必须含 **field-list 拆信封 + item-list 分页**，并扩展契约至 **录制的 gh fixture**。
3. **拆包口范围** 写入方案：含 `project_state_write` + 未来 project 命令；`team.yml` 内联 gh 列迁移清单或豁免理由。
4. **禁止** 三批单 PR 合入替代 **每批活验**；终局同题仅作第四阶段。
5. **删改** 批三对外预期中「不进死亡账」—— 改为「墙可审计、job 仍 fail-closed、可续跑不吞没来由」。
6. **心跳** 标为实验项，附误掐率接受标准，主路径不依赖。
7. **slice 所有权表** 进 schema/文档，防止多记账人覆盖 `validation`/`closeout`。

## 6. 建议改项

1. 利用已有 `budgets.session_outcome` schema 字段（`foreman-run.v1.schema.json` L65–75），lead 也写 session 结局，与 validate 对称。
2. `parse_project_field_list` 与 `parse_project_item_list` 共用 `unwrap_envelope(payload, key)` 减少第三种形状漏网。
3. 批二阶段死亡测试进入 `foreman-wall-ci.yml`，不必等全链活验。
4. 指挥批准改为 **「三批顺序施工 + 分批签字」**，撤回「口头已根治」表述。

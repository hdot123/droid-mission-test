## 一、死因二（W-8 + W-1）— 写板拆盒与分页

### 1.1 方案主张 vs 现码

| 主张 | 核对结果 |
|------|----------|
| `field-list --format json` 返回 dict 信封，`pick_status_option` 当 list 迭代导致 `AttributeError` | **已坐实**。`main` 上 `project_state_write.py` L90–91 直接 `json.loads` 后传入 `pick_status_option`；本席执行：`pick_status_option({"fields":[...]}, "已验收")` → `AttributeError: 'str' object has no attribute 'get'`（遍历 dict 得到键名 `"fields"`）。与方案 §2.1 一致。 |
| W-1 已修 `item-list` 拆盒，W-8 未对称修 `field-list` | **已坐实**。`parse_project_item_list` 存在且单测覆盖；`field-list` 无对应 parse。 |
| 失败仍 fail-closed（`project_state_error` + `run_must_fail` + assemble gate） | **已坐实**。`test_w2_board_write_fail_omits_null_enum` 与 `team.yml` L3267–3274。AttributeError 被 `except` 捕获后同样走路径（非未处理崩溃）。 |

### 1.2 推荐改法评估

**认可（P0）**

- 新增 `parse_project_field_list`，语义对称 `parse_project_item_list`（`list` 直通、`dict` 取 `fields`、否则 `[]`），在 L90 调用——**最小正确 diff**，不碰 PAT、不拆第二写板权威。
- 单测 `test_w8_field_list_dict_envelope` 与现有 `test_w1_*` 范式一致。

**须收窄 / 反对**

1. **W-1 分页写法「`--limit` + cursor/`--after`」**  
   本环境 `gh project item-list --help` 仅见 `--limit`、`--query` 等，**未见 `--after`/cursor 标志**。方案写「以 CLI 文档为准」方向对，但施工图若照抄 `--after` 可能直接卡死。  
   **必改（施工层）**：分页设计改为以 **`--query` 按 issue 过滤**（help 示例支持 `is:issue` 等）为一选；若必须用翻页，先 pin `gh` 版本并抓 **真实 JSON 信封**（是否含 `totalCount`/`pageInfo`），再写循环。单测 mock 应用与 #654 相同的 `{"items":[...]}` 形，而非臆造 cursor 字段。

2. **`field-list` 的 `--limit`（默认 30）**  
   方案只谈 `item-list` limit=200。Status 类字段通常在前 30 内，但若板字段膨胀，`pick_status_option` 仍可能假阴性。施工宜在失败信息中打出 **已解析字段名列表**，或显式 `--limit` 拉大并记入 `closeout`。

3. **其他 GitHub Projects 信封**  
   写板路径仅剩 `project view` 的 `id` 提取（L53–55），当前为 flat dict，**非** W-8 级 bug。全网搜索现码无第二处 `field-list`。方案未要求改 `project view`，**可接受**；但若未来 `view` 也信封化，应共用 parse 族而非再抄一处。

### 1.3 假绿 / 第二权威风险

- 本项修复**降低**假阴性（找不到 item/字段），不削弱 fail-closed；失败仍 `run_must_fail`。  
- **不构成**第二权威路径。

## 二、死因三（W-9）— 领班早死不留痕

### 2.1 「仅成功路径 wall_sync」是否足以推出「失败不上墙」

**部分正确，表述可更严。**

- 方案引用的 L412–438：`Patch and upload ForemanRun wall (lead)` **无 `if: always()`**，且 `--result success` 写死——**已坐实**。
- 更强事实：领班 droid 步（L198）**不写** `droid-exit.txt`（对比 validate L1348–1349）。droid 超时/失败后，后续 `Validate plan` 等步默认 **skipped**，wall sync 与 artifact upload **整段不跑**。因此不仅是「成功才调 sync」，而是 **失败链路上无收尾步**。
- env-check 已上传初始 `foreman-run-${{ run_id }}`（`env-check.yml` L255；lead L67–71 下载）。assemble 下载的往往是**未带 lead 记账的那一版**——与方案 §3.1 一致。

**不足以单独证明「写账步写崩」**（方案亦标存疑）：在现码下，早死更似 **「写账步未跑到」**；「写崩」需 run #179 工件/log，仓库内**无**本席可引用的闭合证据。

### 2.2 推荐改法评估

**认可（P0 核心）**

- lead job 末尾 **`Finalize lead wall (always)`**：捕获退出码 + `team-plan.json` 是否存在 → `wall_sync_job`（或专用脚本）写 `chain.lead`=`failure`/`cancelled`，**`if: always()` upload** `foreman-run.json`——直接对上缺口，且与 validate 采认链 **对称**，不削弱 W-6。

**须收窄（重要）**

1. **`assemble`「synthetic overall=fail、绕过 pick verdict」**（方案 §3.2 P0）  
   - 现 `pick_verdict_from_wall.py` 在无完整 verdict artifact 时 **exit 1**（L99–107），assemble 仅发 minimal 卡（L3276–3291）——这是 **I2 fail-closed**，应保留为默认。  
   - 若施工在 `chain.lead.result!=success` 时 **合成** `final-verdict.json` 并继续 `board_write`，必须同时满足：  
     - `overall` **不得**为 `pass`；  
     - **不得**读取 `needs.*.result` 作为裁决源（I2）；  
     - 合成对象须写入墙字段（如 `closeout.upstream_lead_failed`），且 **pick 步改为显式分支**：「有 authoritative verdict artifact → 原 pick；无 artifact 但链上已记 lead failure → 受限合成 fail」，避免与墙外 JSON 第二源。  
   - 方案写「可复用 `assemble_chain_facts.py`」——**现 `team.yml` 未调用该脚本**（仅注释/文档/单测）。复用前须先解决历史上 W-5「`env_results` 来自 `NEEDS_*` 环境变量」的 **第二权威**隐患（见 `assemble_chain_facts.py` L125–129）。**必改**：W-9 施工说明须写明 **禁止** 把 `needs.lead.result` 注入 `assemble_chain_facts`；链事实只读 **墙 + 工件**。

2. **`chain_facts.summary_code` 扩展**（`lead_timeout` / `lead_no_plan` 等）  
   schema `chain_facts.summary_code` 枚举现为 `ok|not_started|failed|cancelled|...`（`foreman-run.v1.schema.json`），**不含**方案中的细粒度码。施工须 **schema bump + contract 单测**，或暂时落 `summary_code=failed` + `detail` 枚举，避免活验墙 **schema 校验假绿**。

3. **领班 `lead-stream.jsonl` `always()` 上传**（P1）  
   认可为定因手段，但须标 **debug-only**，不进 verdict 契约——方案已暗示，可保留。

### 2.3 假绿风险

- **做错 synthetic 路径**可能：无 verdict 却写出「像收口」的评论且 `overall` 语义含糊 → **假收口感**（非 Actions 假绿）。  
- **做对 always 记账**会降低「九段 unknown」静默洞，**强化**可审计性。

## 三、死因一（W-7 / 会话预算）— A、B 超时

### 3.1 墙上 480+120 vs workflow 600s

| 项 | 核对 |
|----|------|
| `default_budgets()` validator 480+120 / lead 600 | **已坐实**（`foreman_run_lib.py` L33–57） |
| validate droid GNU timeout 默认 600s；仅 I8 标题可改 `VALIDATOR_DROID_TIMEOUT_SECONDS` | **已坐实**（`team.yml` L1343–1348） |
| `budgets.session_outcome` 在 schema 有定义，`compute_validate_conclusion` 会读 | **已坐实**；但 **默认墙无写入**，`session_bad` 分支当前 **永不触发**（`compute_validate_conclusion.py` L25–30） |
| 供应商「同会话 600s 总额、多轮共用」 | **仓库无遥测**；方案标「已坐实（官方定性）」——本席不否认战役叙述，但 **无法从现码独立复现**，施工应维持 **需再查** 等级，避免把 BYOM 行为写进墙枚举的唯一解释 |

### 3.2 「shell 改 480 + adopt 预留 120 = 对齐 W-7」

**仅对齐墙面数字与 GNU 杀点，不对齐供应商总会话限额。**

- 将 shell 降为 480s 可使 **GNU 124** 与 `droid_wall_sec` 一致，并为 adopt（`if: always()`，L1477+）腾出 job 内 wall clock——**逻辑成立**。
- 若 B 路根因是 **会话名 `team-validator` 上累计 600s**（非 GNU），缩短单次 shell **不能**单独证明修复；方案 P2「独立 session 名」标 **存疑** 正确——**本席要求**：不得进入 prod 默认；活验须 **新工单** 且合入 **含 W-7 施工的 main** 后才能验（见 §五）。

### 3.3 TeamDroidSession / stream 记账

- 方向与 `领班制-API硬化修改方案.md` P0-2 一致，**非本轮最小集**。  
- 风险点（方案部分提到、本席加重）：  
  - stream 解析失败须 **fail-closed 写墙**，不得默认 `completion_status=ok` → 否则 **假绿 session**。  
  - 新枚举 `session_budget_exhausted`：`ADOPTION_ERRORS` 为脚本集合，schema 中 `adoption_error` 为 **开放 string**——施工重点是 **文档化 + adopt 分支**，非 schema enum 硬锁。  
  - **禁止**单纯把 `timeout 600s` 改为更大值——方案 §1.5 正确，本席**背书**。

### 3.4 验收独立 session

方案 §1.2 P2 与 §8 存疑表已承认 **无供应商证据**。本席 **反对** 任何暗示「改名即可上线」的表述；仅允许 **test 工单实验 + 网关日志**，且与 prod `SESSION_NAME` 缺省脱钩。
